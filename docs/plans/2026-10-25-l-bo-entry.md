# Tarea L — Entrada del backorder (fila roja + Excel idéntico) (v1457, 2026-10-25)

## Objetivo

Capturar la decisión del vendedor cuando carga unidades para un cliente que ya tiene **backorder vigente** del mismo SKU, sin modales invasivos ni jerga técnica. El vendedor no es técnico; si no entiende el cartel no carga el pedido.

Tres decisiones de Mariano:

1. **Fila roja.** Al cargar un SKU con BO vigente del cliente (importación Excel, alta manual, unificación): la fila se pinta en rojo con la cantidad **NUEVA** (NO suma). La decisión reemplaza el BO previo.
2. **Unificación con el mismo SKU.** La cantidad resultante es la de la orden **MÁS NUEVA**, NO la suma. Si la línea vieja tiene stock asignado se preserva el piso ASIG. Fila roja igual. (Actualiza §56 CLAUDE.md.)
3. **Excel repetido.** Si el Excel completo coincide con una orden abierta del mismo cliente (mismos SKUs y cantidades), antes de cargar nada un cartel con 2 opciones (sí/no cargar).

## 9 principios UX (obligatorios)

1. **Por default no pasa nada.** Sin BO previo, el flujo es idéntico al de hoy.
2. **Con BO previo, nada de modales.** Fila roja en la misma tabla + UNA sola oración en castellano simple + 2 botones. Ejemplo: *"Este cliente ya tiene 20 unidades de este producto esperando stock desde el 12/10. ¿Las 20 que cargaste son las mismas o son 20 más?"* `[Son las mismas (quedan 20)]` `[Son 20 más (quedan 40)]`. El primero preseleccionado. Nada de "backorder", "reconciliar", "unificar". Usar: "esperando stock", "pedido", "producto".
3. **Pasar a Pendientes sigue visible.** Con filas rojas sin resolver, muestra *"Te faltan N productos por revisar"* y al tocarlo lleva a la primera fila roja. NO tira error.
4. **Excel idéntico.** UN solo cartel, una oración, 2 botones: *"Este Excel es igual al pedido N° 435 que ya está cargado desde el 12/10. ¿Es el mismo pedido?"* `[Sí, no cargar nada]` `[No, cargarlo igual]`. Si "cargarlo igual", aplica el punto 2 por fila.
5. **Unificación con el mismo producto.** Misma fila roja, misma oración, mismos 2 botones. NUNCA un modal distinto.
6. **Absorción silenciosa.** El descuento de BO al confirmar (tarea J) es automático y silencioso.
7. **Ícono de ayuda.** Cada fila roja tiene un `?` con una oración de por qué aparece.
8. **Textos en una sola constante.** `src/pure/l_bo_entry_texts.js` para cambiarlos en un PR de 5 min sin tocar lógica.
9. **Captura Playwright de cada estado** con cliente `CLIENTE PRUEBAS E2E` (Paso 0).

## Semántica (regla única)

### `computeBoEntryRows({items, boVigente, clienteCardCode})`

- Input:
  - `items`: líneas que el vendedor cargó (manual, Excel, CPST, unificación). Cada una `{code, qty, origen?, asigRefs?, qtyAsignadaPrevia?}`.
  - `boVigente`: array `[{sku, cantidad, fechaIso, orderNumber?}]` — BO del cliente para los SKUs cargados (fuente: `backorderLines` filtrado por `clienteCardCode`).
  - `clienteCardCode`: string CardCode.
- Output: `[{sku, cantidadNueva, cantidadBoPrevia, fechaBoPrevio, piso, resolved, resolvedQty}]`:
  - `sku`: código SKU.
  - `cantidadNueva`: lo que el vendedor cargó ahora.
  - `cantidadBoPrevia`: suma de BO vigente del cliente+SKU.
  - `fechaBoPrevio`: fecha ISO del BO más viejo (para el mensaje "desde el DD/MM").
  - `piso`: unidades con stock asignado previo (preserva §40). Default 0.
  - `resolved`: `'same' | 'additional' | null`. `null` = la fila sigue roja.
  - `resolvedQty`: cantidad final tras resolver. `same` → max(cantidadNueva, piso); `additional` → cantidadBoPrevia + cantidadNueva, con piso.

Nota: una fila **NO** es roja (no entra en el array) si `cantidadBoPrevia <= 0`.

### `isExcelIdenticalToOpenOrder({items, openOrder})`

- Input:
  - `items`: líneas del Excel cargado `[{code, qty}]`.
  - `openOrder`: una orden abierta del cliente `{_id, orderNumber, items, createdAt}`.
- Output: `{identical: boolean, openOrderNumber?: number, fechaCargaOpenOrder?: string}`.
- `identical=true` ↔ mismo set de `{code→qty}` (case-insensitive en code, mismo total de líneas, mismas cantidades).

Pure. Idempotente. Sin side-effects.

## CF: errorCode UNRESOLVED_BO_ENTRY_ROWS

Payload llega con `lines[i].boEntryResolved` opcional. Si una línea tiene `boEntryResolved === null` (o falta ante BO previo detectado server-side), CF rechaza con:

```json
{
  "ok": false,
  "errorCode": "UNRESOLVED_BO_ENTRY_ROWS",
  "message": "El vendedor tiene que decidir qué pasa con el backorder previo",
  "data": {
    "rows": [{"sku": "1234", "cantidad": 20, "boAnterior": 20}]
  }
}
```

Nota: el CF **no** vuelve a buscar BO en Firestore para disparar este error (sería un recomputo caro). La lógica es: **si el payload tiene filas con `boEntryResolved===null`, rechaza**. El cliente ya debió resolver todas las rojas antes de enviar. (En otras palabras: es un gate en el payload, no una revalidación.)

## Playwright E2E (4 escenarios)

1. Excel idéntico → "Sí, no cargar nada" cancela.
2. Excel idéntico → "No, cargarlo igual" sigue el flujo con filas rojas.
3. Fila roja → "Son las mismas (quedan 20)" resuelve y la fila deja de ser roja.
4. Fila roja → "Son 20 más (quedan 40)" resuelve con suma + sigue roja hasta la decisión.

Capturas en `tests/e2e/evidencia/<fecha>/ola2_l_final/`.
