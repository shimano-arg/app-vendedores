## Contexto E10

El Cloud Function `functions/core/commit-pedido-core.js:840` setea en todo pedido que crea:

```js
_commitVersion: 'commitPedidoCore_v1',
```

Ningún call-site cliente setea ese campo (`grep -n _commitVersion index.html` → cero matches). Por lo tanto `_commitVersion == 'commitPedidoCore_v1'` es un **marker fiable** de "pasó por el CF". La idea de E10 es cerrar la rule `pedidos.create` a `request.resource.data._commitVersion == 'commitPedidoCore_v1' && ...` para que ningún cliente pueda escribir pedidos legacy — forzando el pipeline server-side con lock §64.3, STOCK_CHANGED diagnóstico §64, draft idempotency, etc.

Criterios acordados en el prompt:

- (a) `pedidos` activos (`closedAt == null`) con `_commitVersion` ausente → **debe ser 0**.
- (b) `pedidos` creados desde el jueves 2026-10-22 00:00 ART (`2026-10-22T03:00:00Z`) sin `_commitVersion` → **debe ser < 5**.

Si ambos pasan: migración completa, cerrar rule. Si no: investigar quién sigue escribiendo legacy.

## Hallazgos del análisis estático (sin ADC)

### Hallazgo 1 — `_gbConfirmar` escribe pedidos sin pasar por CF

**Archivo**: `index.html:19324`
**Función**: `_gbConfirmar` (modal "Generar Backorder" manual)
**Flow**: VDE/admin arma un backorder manual (cliente + N SKUs sin stock) → clic "Confirmar" → `fbDb.collection('pedidos').add(docData)` directo.

Shape del payload que escribe:

```js
{
  // ...clientName, lines[], netAmountArs, discountPct, ...
  schemaVersion: 2,
  transferidoSAP: {
    via: 'manual-backorder',
    skipSap: true,          // <-- NUNCA entra a SAP
    docNum: null,
    docEntry: null,
    createdAt: nowIso,
  },
  source: 'manual-backorder',
  createdAt: FieldValue.serverTimestamp(),
  // SIN _commitVersion. Hoy la rule lo permite.
}
```

**Si cerramos `rules.pedidos.create` a `_commitVersion == 'commitPedidoCore_v1'`, `_gbConfirmar` se rompe inmediatamente.** VDE/admin ya no puede crear backorders manuales desde la UI.

**Opciones** (NO implementadas en esta tarea — son fix, no auditoría):

1. **Mover GB al CF**: ampliar `commitPedidoCF` para aceptar `origen: 'manual-backorder'` + `skipSap: true` como caso válido. GB queda detrás del mismo lock §64.3 que los demás pedidos.
2. **CF separado `commitBackorderManualCF`**: endpoint específico que setea `_commitVersion = 'commitBackorderManual_v1'` y la rule acepta ambos literales.
3. **Rule parcial**: `allow create: if hasCommitVersion || hasManualBackorderMarker` — se mantiene el pasaje directo para GB con un marker alternativo. Menos seguro.

Opción recomendada: (1) o (2). (3) deja la puerta abierta.

### Hallazgo 2 — Fallback legacy en `doConfirmPedido`

**Archivo**: `index.html:36664`
**Flow**: `doConfirmPedido` intenta primero `window._tryCommitPedidoCF(docData)`. Si CF OK → usa `pedidoId` server. Si CF devuelve error codificado (VERSION_OLD, STOCK_CHANGED, etc.) → modal + `return`. **Si CF NO está disponible** (null, timeout, excepción) → cae a `fbDb.collection('pedidos').add(docData)` directo.

Comentario del propio código: `// Fallback legacy (CF no disponible): seguir con pedidos.add directo.`

Este fallback es un "escape hatch" por si el CF está caído en producción. Al cerrar la rule, ese escape desaparece: una caída del CF rompe toda la operación de pedidos (no sólo degradación — bloqueo completo).

**Opciones**:

1. **Eliminar el fallback** (lo esperable con E10 completo). Si CF cae, modal "Reintentá en 1 min". Trade-off: downtime de CF = downtime de pedidos.
2. **Dejar el fallback pero deployar bump de versión** para que la rule acepte ambos path. Pierde el punto de E10.

Opción (1) es la coherente con el espíritu de E10. Deployar sólo cuando la caída del CF no sea una posibilidad razonable (hoy el CF tiene revisión reciente y 0 incidentes).
